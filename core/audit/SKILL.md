# audit


## Overview

`audit` is the pre-merge gate for `feature` and `system-change` task classes (see `core-config` §8 task-class rubric). It is the load-bearing implementation of charter v1.1 §2.3 *independence-of-reviewer*: the audit sub-agent runs in a fresh context with the diff + spec + threat-model + `decisions.md` only, never with the implementation transcript. This resists three predictable degradations the panel named in [E1 F5; E3 §3.4]:

- **Rubber-stamping** — auditor returns "no issues" on a sloppy diff.
- **Paranoid hallucination** — auditor flags everything HIGH because it has no project context.
- **Severity laundering** — CRITICAL findings reframed as "out of scope".

The skill folds v0.1's separate `audit-security` and `audit-pe` per panel §1.4: empirical overlap on real diffs is 60–70% (perf bugs are often correctness bugs; maintainability findings are often security findings). One audit with two severity dimensions ships now; split only if 8+ weeks of dogfood reveal divergence.

## When to use

Auto-invokes when the user's prompt contains any of: `audit`, `security review`, `vulnerability`, `pre-merge audit`, `principal engineer review`, `compliance review`.

Manually invoke before:

- Merging any `feature` or `system-change` PR (per charter v1.1 §3 phase 8/9).
- Releasing a hotfix that touched authn/authz/payment/PII paths.
- Bumping a dependency that crosses a trust boundary.

Do NOT use for:

- Style-only nits or `refactor(scope):` no-behavior-change diffs — use `delta-code-review` (P0-05) instead. `audit` is heavier, slower, and Opus-priced.
- A diff you have not yet committed and have not yet asked `delta-code-review` to triage. `audit` is the *second* gate, not the first.

## Core pattern

```
spec.md  ─┐
diff      ├─►  fresh sub-agent (Opus, isolated worktree)
threat.md ├─►     ├─ apply security checklist
decisions ├─►     ├─ apply PE checklist
          ─┘     └─ emit findings JSON + report.md
```

The auditor's context is the four input artifacts plus read-only access to the worktree. It does not see the implementation chat history, the user's instructions to the implementer, or the implementer's own self-assessment. This is the independence guarantee.

## Implementation

The skill is invoked through `safe-spawn-claude.sh` (operator tool, not part of `core/`) in background mode:

```bash
# Symlink opinions/safe-spawn-claude.sh into a PATH directory (e.g. ~/bin/)
# so this invocation stays portable across operator layouts.
safe-spawn-claude.sh \
  $CLAUDE_PROJECT_DIR/core/audit/prompts/system.md \
  claude-opus-4-7 \
  "audit-${FEATURE_ID}" \
  $CLAUDE_PROJECT_DIR
```

The sub-agent reads, in order:

1. `prompts/independence-preamble.md` — the "you did NOT write this code" reminder.
2. `prompts/system.md` — main system prompt with task instructions.
3. `prompts/security-checklist.md` — security-dimension findings list. **Every security finding MUST carry both `OWASP:A0X` and `STRIDE:<letter>` tags** per the file's "Tagging requirement (ADOPT-03)" section; the audit verdict cites at least one OWASP or STRIDE category for every HIGH/CRITICAL finding.
4. `prompts/pe-checklist.md` — principle-engineering-dimension findings list.
5. `prompts/glossary.md` — canonical vocabulary (severity / STRIDE / finding categories / banned phrases). Read from `$AUDIT_GLOSSARY_PATH` (CI: PR base-SHA temp file) or fall back to `core/audit/prompts/glossary.md` at working-tree HEAD (local `/audit`, advisory). Missing-on-base or missing-locally is non-fatal; the auditor falls back to prose vocabulary in items 2–4.
6. The diff, spec, threat-model, and `decisions.md` from the inputs the user pinned in the spawn prompt.

## Inputs (what the user provides)

| Input | Required | Default |
|---|---|---|
| `<id>` | yes | — |
| Diff range | no | `git diff main...HEAD` |
| `--dim` | no | `security,pe` (both) |

If a required input is missing, the auditor MUST refuse to run and report the gap rather than synthesise findings without context (paranoid-hallucination guard, [E1 F5]).

When `decisions.md` (charter §4 phase 6) contains a VERDICT block emitted from `core/core-config/templates/idea-rubric.md`, the auditor treats the recorded WHAT-WOULD-CHANGE-MY-MIND condition as a calibration anchor for the audit's necessity / risk findings — i.e. if the decision was ADOPT contingent on a falsifiable condition and the diff fails to satisfy it, surface that as a HIGH finding rather than re-litigating the adoption decision.

## Outputs


1. **Executive summary** — counts by severity × dimension, overall verdict (PASS / BLOCK).
2. **Checklist** — every line item from `security-checklist.md` and `pe-checklist.md` marked `[x]` (passed), `[!]` (finding), or `[-]` (not applicable, with reason).
3. **Findings table** — one row per finding: `id | severity | dimension | where | description | recommended_fix | references`.
4. **Sources** — every external claim cites a panel finding, charter section, or external URL.

Structure mirrors `examples/clean-report.md` (PASS) and `examples/dirty-report.md` (BLOCK).

## Severity scale

| Severity | Meaning | Verdict gate |
|---|---|---|
| CRITICAL | Production data loss, RCE, auth bypass, PII leak | BLOCK; zero-deferral |
| HIGH | Privilege escalation, broken invariant, data corruption window | BLOCK; zero-deferral |
| MEDIUM | Defence-in-depth gap, contract drift, test gap on critical path | Negotiable; document |
| LOW | Code-smell that compounds risk, missing log, hardcoded value | Track; do not block |
| INFO | Observation, no required action | Informational |

Zero-deferral on CRITICAL or HIGH per charter v1.1 §6.1. The auditor cannot reclassify CRITICAL → MEDIUM under "out of scope" pressure (severity-laundering guard).

## Finding lifecycle: id / cycle / status (ADOPT-02 v1.1.1)

Every finding object validates against `schemas/finding.json` and MUST carry three lifecycle fields beyond severity/dimension:

- `id` — `<DIM>-<NNN>` (e.g. `SEC-001`, `PE-042`). Stable across re-audit cycles so the implementer can reference *"fix SEC-001 from cycle 1"*.
- `cycle` — `1`, `2`, or `3`. Cycle 1 is the first pass; cycles 2–3 are re-audits after the implementer addressed prior findings. After cycle 3 the finding MUST move to `status: ESCALATED` rather than entering a fourth cycle (forces human decision over perpetual loops).
- `status` — `OPEN` (newly emitted), `IN-PROGRESS` (implementer working on it), `RESOLVED` (fix verified by re-audit), `ESCALATED` (unresolved after cycle 3), `ACCEPTED-RISK` (explicit human sign-off to ship without fix).

`ACCEPTED-RISK` is allowed only for MEDIUM / LOW / INFO findings. CRITICAL and HIGH retain zero-deferral and cannot be downgraded to `ACCEPTED-RISK` — they must be `RESOLVED` or `ESCALATED`.

## Common mistakes

- **Spawning `audit` without `safe-spawn-claude.sh`.** Direct `claude -p ...` invocations bypass the daily budget, dedup, and active-session guards. See user CLAUDE.md "Sub-agent spawn — PHẢI qua safe-spawn-claude.sh".
- **Running `audit` on every commit.** It is a phase-8/9 gate, not a continuous review. Use `delta-code-review` for commit-by-commit triage.
- **Letting the auditor see the implementation chat.** Defeats the entire principle. The sub-agent must spawn with isolated context.
- **Allowing the auditor to fix code.** The auditor produces a report; the implementer fixes the findings and re-runs `audit`. Mixing roles re-introduces anchor bias.
- **Downshifting model to Sonnet for cost.** Forbidden — see `README.md` "Model selection" section. Audit is one of the highest-leverage uses of Opus and one of the lowest-frequency invocations; the cost math always favours Opus.

## Install

`git pull` only. The `ai_disclaimer:` literal lives in this file's frontmatter
and is read at audit spawn from your working tree. The `audit-required.yml`
CI workflow's existing tampering-detection on `core/audit/` enforces base-SHA
integrity for PRs (defense-in-depth from `audit-builtin` AUDIT-002 carries
over without a workflow edit). The spawn-time read of working-tree SKILL.md
is the install path for the disclaimer.

For the v1.2+ `prompts/glossary.md` vocabulary file, downstream installations
that copy `core/audit/prompts/` into `$CLAUDE_HOME/skills/audit/prompts/` should
also run `bash core/governance-pack/install.sh --refresh-prompts` after
`git pull` to re-sync the prompt files idempotently. CI uses the base-SHA
temp file at `$AUDIT_GLOSSARY_PATH`, so the installer flag is operator
ergonomics, not a CI dependency. See `core/audit/README.md` §"Install" for
the local-vs-CI sourcing distinction.
